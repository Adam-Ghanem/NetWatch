# Pre-auth throttle: stale peer reclamation

The in-process failure limiter stores a bounded number of transport-peer buckets. When all slots are occupied, failures for additional peers share an overflow bucket. `retry_after()` reclaims expired peer buckets before consulting that shared overflow for an *unknown* peer. Reclamation is gated by the earliest possible peer-event expiry, so a full map is not scanned on every new-peer failure while all stored buckets are still active. Otherwise, an expired peer could occupy the last slot and cause an unrelated fresh peer to receive HTTP 429 until another failure triggered cleanup.

After a sweep, the limiter recomputes the next earliest expiry; read and write overflow paths skip another O(max-peers) sweep until that time. Expired slots can therefore be reclaimed with at most one full sweep per earliest-expiry boundary. Renewing an existing peer bucket never advances an already-due watermark: otherwise that renewal could hide a different stale bucket until a later window. The watermark only moves earlier when a new earliest expiry is observed, and is recomputed after each sweep. Existing peers still use their own rolling-window history. If every peer slot remains active, unknown peers still share overflow throttling. This change does **not** clear overflow, bypass active limits, trust `X-Forwarded-For`, store credentials, or widen network authorization.

Regression: `tests/test_auth_throttle.py::test_fresh_peer_does_not_inherit_overflow_after_stale_slot_expires` uses a deterministic monotonic clock to prove that a fresh peer is unblocked after stale-slot expiry while its stored overflow history remains intact; overflow throttling applies again if all peer slots are occupied. The separate `test_active_peer_capacity_keeps_overflow_throttled` regression verifies that unknown peers remain blocked while every peer slot is still active. `test_full_peer_map_sweeps_only_when_a_peer_bucket_can_expire` verifies that active buckets are not rescanned for every overflow attempt and that reclamation resumes at the next expiry. Run `pytest -q tests/test_auth_throttle.py` and the normal Python/Security CI before merging.

The limiter is process-local, not a distributed edge defense. Multi-worker deployments still need trusted upstream controls. No production traffic, active probing, or credential material is needed to validate this fix.
